# ProjectAsset30
-Week1 Started
## 実行方法

Python環境で `pip install -r requirements.txt` を実行し、環境変数
`OPENAI_API_KEY` を設定してください。キーをソースやMarkdownに記載しないでください。
モデルは `src/config.py` の既存設定を使用します。

```sh
python src/manager.py
```

既存のメニュー1～3は手動実行です。メニュー6「自動実行」を選び、調査テーマを
1回入力すると、Research AI → Blog AI → Note AI の順に実行します。
各段階で `data/research/<テーマ>.md`、`data/blog/<テーマ>.md`、
`data/note/<テーマ>.md` にUTF-8で保存し、次のAIは直前に保存された記事を読み込みます。
同じテーマを更新すると、旧記事を履歴へ保存してから最新記事を置き換えます。
空のテーマ、パス区切り、Windowsで使用できないファイル名などは拒否します。

API呼び出しや保存に失敗すると後続を停止してメニューに戻ります。
保存済みの結果は残ります（全段階を巻き戻す機能や自動再試行はありません）。
`python src/main.py` の単独リサーチも共通の費用確認と保存履歴を利用します。

## テスト

```sh
python -m unittest discover -s tests -v
```

API境界をモックし、一時ディレクトリへ実際にMarkdownを保存します。
APIキー・外部通信・API利用料金は不要です。


## 費用管理

テーマや元記事を選んだ後、APIを呼ぶ前に費用概算を表示します。
`y` を入力すると実行し、それ以外はキャンセルします。
自動実行は3段階分をまとめて1回確認し、手動実行は選択したAIの費用を確認します。
キャンセル時はAPI呼び出し・ファイル保存を行いません。

`src/config.py` で以下を変更できます。

| 設定 | 初期値 | 用途 |
|---|---|---|
| `MAX_OUTPUT_TOKENS` | 3000 | 1回の推論を含む出力上限 |
| `MAX_INPUT_BYTES` | 12000 | プロンプト全体のUTF-8バイト数制限 |
| `REASONING_EFFORT` | low | 推論量の設定 |
| `USD_TO_JPY` | 150 | 円表示用の仮定レート |
| `MODEL_PRICES` | GPT-5.5：入力$5／出力$30 | 100万トークンあたりの標準単価 |

単価は[公式モデル情報](https://developers.openai.com/api/docs/models/gpt-5.5)を
2026-10-11に確認した値です。モデルを変更する場合は対応する料金も設定してください。
料金設定のないモデルや不正な上限ではAPIを呼ばず停止します。

概算は、UTF-8バイト数を入力トークン数の保守的な目安とし、出力は上限まで使う前提です。
自動実行では後続記事の長さが未確定のため、3回とも入力上限を使って見積もります。
初期設定で自動実行は **$0.45（約67.5円）** の目安です。
実請求の上限保証ではなく、換算レートは最新為替ではありません。
完了時・途中停止時に、取得できた使用量から費用を表示します。
キャッシュ割引・税・手数料は計算に含めません。使用量が取得できない呼び出しは
計算対象外と明示します。使用量の項目が欠けている・値が不正な場合も同様に扱い、
それだけで正常な記事生成を止めません。送信前のクライアント初期化失敗はAPI呼び出しに数えません。
応答後のクライアント終了・記事検証・保存の失敗でも、取得済みの使用量は集計に残します。
請求額はOpenAIの請求画面で確認してください。

APIの自動再試行は無効です。各呼び出しはタイムアウト120秒です。
入力上限を超えた場合は、元記事を切り捨てず、API送信前に停止します。
出力上限などで応答が未完了になった場合も費用は発生し得ますが、
不完全な記事を保存したり次のAIへ渡したりしません。必要に応じて上限を調整してください。

## 保存履歴

最新版はこれまでどおり `data/<research|blog|note>/<テーマ>.md` に保存します。
更新前の記事は `data/<research|blog|note>/history/<テーマ>/<UTC日時>_<ID>.md`
に退避します。既存の記事も初回の更新時にそのまま保存されます。
履歴はエクスプローラーやエディターで開けます。手動の記事選択には最新版だけが表示されます。

旧版の退避が成功してから、新しい記事を一時ファイルから置き換えます。
退避や置き換えに失敗した場合は旧版を維持して停止します。
並行実行の調停・履歴の自動削除・途中からの再開は未対応です。

## 記事品質チェック（API料金0円）

`python src/manager.py` のメニュー **7** を選び、Research・Blog・Noteと記事番号を
選択してください。既存の生成メニュー、費用管理、保存履歴はそのまま利用できます。
品質チェックはPython標準ライブラリだけで行い、API呼び出し・生成処理は行いません。
単独の入口 `python src/quality_check.py` でも利用でき、APIキーやOpenAI SDKは不要です。

総合結果「合格／要確認」、項目ごとの結果、問題点、改善案を画面に表示し、
`data/quality/<research|blog|note>/<テーマ>/<UTC日時>_<ID>.md` に新規保存します。
元記事・記事履歴は変更せず、以前のチェック報告書も上書きしません。
点検した版を識別するため、元記事のSHA-256を報告書に記録します。

| 項目 | 点検方法 |
|---|---|
| 文字数 | 空白、見出し、コード、主なMarkdown記号を除いた本文の文字数 |
| 見出し | タイトル1つ、本文見出しの数、見出し階層の飛びを確認 |
| 本文 | 見出し・コードだけで本文が空になっていないか |
| 重複文章 | 空白・主な装飾記号を除いて同一の20文字以上の文・行が複数あるか |
| 未完成表現 | ここに入力、ここに記入、本文を入力、タイトルを入力、TODO、TBD、FIXME |
| Markdown | 見出しの空白・空見出し・7個以上の#、閉じないコードフェンス、太字記号の対応、空URLのリンク |

文字数と本文見出しの目安は `src/quality_check.py` の `PROFILES` に設定しています。
Researchは300～12000文字・本文見出し2個以上、Blogは600～16000文字・3個以上、
Noteは400～12000文字・3個以上です。文字数は読みやすさを保証する基準ではなく、
用途によって調整する目安です。`#`形式と下線形式の見出しを扱い、コード内の見出しやTODOは除外します。未完成表現の点検では、フェンス付きコードに加え、
同じ長さのバッククォートで閉じたインラインコードも除外します（見出し内や段落内の改行を含む）。
閉じていない・エスケープされたバッククォートはコードの囲みと見なしません。
日本語に隣接するTODO／TBD／FIXMEも大小文字を区別せず検出します。
英数字・アンダースコアに隣接する識別子の一部（TODOLIST、myTODO、TODO_item等）は対象外です。

例：短いBlog記事に「ここに入力」や同じ長文の繰り返しがある場合、総合結果は「要確認」となり、
文字数・未完成表現・重複文章の問題候補と改善案が表示されます。

**「合格」は対象ルールで問題候補が見つからなかったという意味です。事実関係・正確性・公開適否は保証しません。**
出典の検証、最新情報の確認、類似した意味の文章の検出、Markdown仕様全体の検証は行いません。
引用や意図的な繰り返し等を「要確認」とする場合があります。記事を自動修正せず、
公開前に人間が指摘箇所と出典・内容を確認してください。


## 新規保存時の見出し整理

記事タイトルは保存側が `# テーマ` として1つ付与します。Research・Blog・Noteの生成指示は本文のみを求め、主要見出しを `##`、小見出しを `###` とします。単独実行とパイプラインの両方に適用されます。

生成本文の先頭（空行を除く）が保存タイトルと同じ `#` 見出しの場合だけ、保存側のタイトルに統合し本文を保持します。本文中の同名見出しや異なる `#` は意味や子見出しを壊さないようそのまま残し、確認を促します。

正常な見出しは空白・改行を含めて保持します。本文全体が `###` 以降で始まり、内部に階層の飛びや曖昧な形式がない場合のみ、大小関係を変えず全体を同じ段数だけ浅くします。内部の飛びは親見出しの欠落か意図した構造か判断できないため保持して警告します。3段を超える階層、下線形式の見出し、形式不明の見出し、閉じていないコードフェンスも無理に修正せず警告します。

フェンス付き・インデント付きコード、引用、本文中の通常の `#` は変更しません。タイトルと本文の見出しを整理しても、見出し数不足や文字数不足、TODO等の問題は品質チェックで引き続き指摘されます。事実関係や公開適否は保証しません。

過去記事の一括修正は行いません。通常の再生成時は従来どおり旧記事を履歴に保存し、新しい記事のみ整理します。見出し整理にAPI料金は発生しません。
