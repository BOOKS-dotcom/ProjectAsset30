# Git

【概要】

Gitは、ソースコードや文書などの変更履歴を管理するための「分散型バージョン管理システム」です。  
2005年にLinuxカーネル開発のため、Linus Torvaldsによって開発されました。

現在では、ソフトウェア開発における事実上の標準ツールとなっており、GitHub、GitLab、Bitbucketなどのサービスと組み合わせて広く利用されています。

Gitの主な目的は、以下のような作業を効率化することです。

- ファイルの変更履歴を記録する
- 過去の状態に戻す
- 複数人で同時に開発する
- 機能追加や修正をブランチで分けて管理する
- コードレビューやリリース管理をしやすくする

Gitは「分散型」であるため、各開発者のPCにリポジトリ全体の履歴が保存されます。  
そのため、ネットワークに接続していなくても履歴確認やコミットなどの作業が可能です。

---

【重要ポイント】

1. GitとGitHubは別物

Gitはバージョン管理システムそのものです。  
一方、GitHubはGitリポジトリをインターネット上で管理・共有するためのホスティングサービスです。

似たサービスには以下があります。

- GitHub
- GitLab
- Bitbucket
- Azure Repos

Gitを使うだけならGitHubは必須ではありませんが、チーム開発ではGitHubなどと組み合わせることが一般的です。

---

2. 基本的な概念

Gitを理解するうえで重要な概念は以下です。

- リポジトリ  
  ファイルと変更履歴を管理する場所

- コミット  
  ある時点の変更内容を記録する単位

- ブランチ  
  開発作業を分岐させる仕組み

- マージ  
  別のブランチの変更を統合すること

- リモートリポジトリ  
  GitHubなど外部サーバー上にある共有リポジトリ

- クローン  
  リモートリポジトリを自分の環境にコピーすること

- プル  
  リモートの変更を取得して自分の環境に反映すること

- プッシュ  
  自分の変更をリモートに送信すること

---

3. Gitの基本的な作業フロー

一般的なGitの作業手順は以下のようになります。

1. リポジトリをクローンする  
2. 作業用ブランチを作成する  
3. ファイルを編集する  
4. 変更内容をステージングする  
5. コミットする  
6. リモートにプッシュする  
7. Pull Request / Merge Requestを作成する  
8. レビュー後、メインブランチにマージする

代表的なコマンド例は以下です。

```bash
git clone <repository-url>
git checkout -b feature/new-function
git status
git add .
git commit -m "Add new function"
git push origin feature/new-function
```

---

4. ブランチ戦略が重要

Gitをチームで使う場合、ブランチの運用ルールが重要です。

代表的なブランチ戦略には以下があります。

- Git Flow  
  main、develop、feature、release、hotfixなどを使う比較的厳格な運用

- GitHub Flow  
  mainブランチとfeatureブランチを中心としたシンプルな運用

- GitLab Flow  
  環境別ブランチやデプロイフローと組み合わせた運用

近年は、継続的デリバリーや小規模リリースの普及により、GitHub Flowのようなシンプルな運用が好まれる傾向があります。

---

5. コードレビューとの連携

GitはPull RequestやMerge Requestと組み合わせることで、コードレビューの中心的な仕組みになります。

コードレビューでは以下を確認します。

- バグがないか
- 設計が適切か
- セキュリティ上の問題がないか
- コーディング規約に沿っているか
- テストが追加・更新されているか

Git単体は履歴管理ツールですが、GitHubなどと連携することで、開発プロセス全体を支える基盤になります。

---

6. CI/CDとの相性が高い

GitはCI/CD、つまり継続的インテグレーション・継続的デリバリーの起点として使われます。

例えば、GitHub Actions、GitLab CI/CD、CircleCI、Jenkinsなどと連携すると、以下の処理を自動化できます。

- テスト実行
- 静的解析
- ビルド
- デプロイ
- セキュリティスキャン
- リリース作成

現在のソフトウェア開発では、GitへのプッシュやPull Request作成をきっかけに自動処理が走る構成が一般的です。

---

7. セキュリティ面での注意

Gitでは一度コミットした情報が履歴に残るため、機密情報の扱いに注意が必要です。

特に以下の情報をコミットしてはいけません。

- パスワード
- APIキー
- 秘密鍵
- アクセストークン
- 個人情報
- 本番環境の設定ファイル

誤ってコミットした場合、単にファイルを削除しても履歴には残るため、履歴の書き換えやキーの無効化が必要になります。

対策としては以下が有効です。

- `.gitignore`を適切に設定する
- secret scanningを導入する
- 環境変数やシークレット管理サービスを使う
- コミット前チェックを導入する

Gitは便利な一方で、初心者にはやや難しい概念もあります。

- revert

ただし、エンジニアだけでなく、デザイナー、ライター、データサイエンティスト、研究者などにも利用が広がっており、今後も重要な基礎スキルであり続けると考えられます。

【今後注目すべき点】

1. AI開発支援ツールとの連携

GitはAIコーディング支援ツールとの連携がさらに進むと考えられます。

例えば以下のような用途です。

- コミット内容の自動要約
- Pull Request説明文の自動生成
- コードレビューの自動化
- バグ修正候補の提案
- セキュリティリスクの自動検出
- 変更履歴からのドキュメント生成

GitHub Copilot、GitLab Duo、CodeRabbitなどのように、Gitの履歴やPull RequestをAIが解析する流れは今後さらに強まるでしょう。

---

2. セキュリティ管理の強化

ソフトウェアサプライチェーン攻撃の増加により、Gitリポジトリのセキュリティはますます重要になります。

今後は以下がより重視されます。

- コミット署名
- 依存関係の脆弱性チェック
- secret scanning
- branch protection
- 2要素認証
- SBOMとの連携
- SLSAなどの供給網セキュリティ基準

特に企業利用では、「誰が」「いつ」「どの変更を」「どの権限で」行ったかを追跡できることが重要になります。

---

3. モノレポ運用の拡大

複数のプロジェクトやサービスを1つのリポジトリで管理する「モノレポ」運用にも注目が集まっています。

モノレポのメリットは以下です。

- 共通ライブラリの管理がしやすい
- 横断的な変更が容易
- 開発ルールを統一しやすい
- 依存関係を把握しやすい

一方で、リポジトリが巨大化しやすく、ビルド時間や権限管理が課題になります。

そのため、今後は以下のような技術との組み合わせが重要になります。

- sparse checkout
- partial clone
- build cache
- Bazel
- Nx
- Turborepo

---

4. GitOpsの普及

GitOpsは、インフラやアプリケーションの状態をGitで管理し、Gitへの変更を起点に自動的に環境へ反映する運用手法です。

特にKubernetes環境で広く使われています。

GitOpsの特徴は以下です。

- Gitを唯一の信頼できる情報源にする
- インフラ変更をPull Requestで管理する
- 変更履歴を監査しやすい
- ロールバックが容易
- 自動デプロイと相性が良い

代表的なツールには以下があります。

- Argo CD
- Flux
- Jenkins X

クラウドネイティブ開発の拡大により、GitOpsは今後も重要性が増すと考えられます。

---

5. 大規模リポジトリ対応

Gitは非常に強力ですが、巨大なリポジトリや大量のバイナリファイルを扱う場合には課題があります。

そのため、今後も以下のような機能や周辺技術が重要になります。

- Git LFS
- partial clone
- sparse checkout
- shallow clone
- 仮想ファイルシステムとの連携
- 高速な差分取得

ゲーム開発、AIモデル管理、大規模Webサービス開発などでは、Gitのパフォーマンス最適化が重要なテーマになります。
